## bot_responsible Issue 分析经验

### 1. 功能请求识别与降级兜底
- 遇到“加/新增/支持/希望”等诉求，尤其是“被禁言时向 Bot 主转发禁言前聊天记录、数量可配置”“新增通知 QQ 号接收插件通知”，应优先归类为 `feature` / `enhancement`，不要因标题无意义、API 429/配额耗尽或格式校验失败降为 `other`。
- 标题为“。”、空标题或纯符号时，必须从正文抽取核心意图生成标题；若原标题已清晰，可说明建议保留。
- 标题中的显式标记要高权重利用：`[feature]`→功能请求，`[bug]`→缺陷，`[medium]`→优先级参考；正文一致时提高置信度。
- AI/API 失败时启用本地规则兜底：关键词“禁言/转发/聊天记录/配置/合并转发/不填/默认值/通知 QQ/私聊通知”至少推出分类、基础标签、标题、谨慎重复检测和可行性拆解。

### 2. 配置默认值与通知类需求
- 用户说“不填/为空”时，不要直接假设落盘值；需区分 key 缺失、`None`、`""`、`0`、`"0"`。`config.get(key, default)` 只处理缺失，不处理已存在的空值或 0。
- 对 `ban_forward_history_count` 一类配置，要同步检查代码默认值、配置 schema、README/说明、设置 UI 保存行为；若 `int("")` 会异常回退 20，则“不填不转发”根因可能是 UI/schema 将空值保存为 0。
- 新增“通知 QQ 号”这类需求时，要明确通知群、指定 QQ、管理员兜底的优先级与是否可并发发送，并考虑私聊权限/好友关系限制。
- 标签建议优先贴合仓库实际标签；未知时也不能空白，至少给低风险标签 `bug` 或 `enhancement`，并可结合 `configuration`、`notification`、`needs discussion`、`needs info`。

### 3. OneBot / QQ 昵称类问题
- 用户使用 `/QQ昵称`、`/群XXX` 等指令，调用 OneBot 标准接口但行为与预期不符时（如 `set_qq_profile` 返回成功但昵称未变），优先归类为 `bug` 或 `support`，优先级通常 `low`～`medium`。
- 这类问题常是 OneBot 实现兼容性、平台限制、权限/风控、缓存未刷新或调用回验不足，不要直接归为 `other`。
- 可行性重点分析：实现是否支持昵称写入、是否需要二次回读、回读接口是否可靠、是否要补充日志与原始响应、文档是否需标注兼容性。
- 标题模板：`使用 /{指令} {参数} 后未生效（{接口} 返回与实际行为不一致）`。
- 标签建议：`bug`、`onebot`、按具体功能加 `profile`/`group`/`config`、`needs-triage`、`needs info`。

### 4. 重复检测与标题生成
- “未检测到重复”必须谨慎，除非说明检索依据；更稳妥写法是“暂未发现重复，但需结合历史 Issue 确认”。
- 对相关 Issue 应检索：禁言、mute、ban、合并转发、聊天记录、主人通知、配置项名、`notify_qq`、`set_qq_profile`、`nickname`、`profile` 等关键词。
- 不要盲目把优先级塞进标题，除非仓库确有该风格；标题应聚焦业务对象、触发条件和异常/诉求。
- 标题改写不要引入未提及结果，也不要仅输出“无建议”。

### 5. 审查与修复类通用经验
- 配置解析必须区分空值、默认值和显式关闭；避免把 `0`、`"0"` 误吞成默认值。
- 小修复也应建议最小测试矩阵：缺失、`None`、空字符串、纯空白、`0`、`"0"`、合法数字、非法字符串、越界值。
- 对外部 API 返回成功但实际状态不一致的问题，优先做更明确的失败提示、调用回验、文档说明和兼容性标注，不要强行假定插件端必然可修复。
