## bot_responsible Issue 分析经验

### 1. 功能请求识别与降级兜底
- 遇到“加/新增/支持/希望”等诉求，尤其是“被禁言时向 Bot 主转发禁言前聊天记录、数量可配置”，应优先归类为 `feature` / `enhancement`，不要因标题无意义、API 429/配额耗尽或格式校验失败降为 `other`。
- 标题为“。”、空标题或纯符号时，必须从正文抽取核心意图生成标题，例如：`支持在 Bot 被禁言时向主人转发禁言前聊天记录`；若原标题已清晰，可说明建议保留。
- 标题中的显式标记要高权重利用：`[feature]`→功能请求，`[bug]`→缺陷，`[medium]`→优先级参考；正文一致时提高置信度。
- AI/API 失败时启用本地规则兜底：关键词“禁言/转发/聊天记录/配置/合并转发/不填/默认值”至少推出分类、基础标签、标题、谨慎重复检测和可行性拆解，避免结果空白。

### 2. 禁言转发类需求评估
- 该类需求通常优先级为 `medium`：对 Bot 管理、封禁溯源和群治理有价值，但非崩溃/安全阻断；若仅辅助功能或实现条件不足可降为 low。
- 可行性应拆为：是否能监听 Bot 自身被禁言事件、是否已有 per-group 最近消息缓存/环形缓冲区、是否支持合并转发、是否有配置系统、是否能只发给主人。
- 若无合并转发能力，应建议退化为普通文本/摘要转发；工作量一般中等，依赖平台事件与转发 API。
- 必须强调隐私/权限风险：自动转发群聊记录给 Bot 主可能涉及敏感信息，建议默认关闭、数量限制、权限边界清晰、必要时脱敏，并标记 `privacy` / `needs discussion`。
- 标签建议优先贴合仓库实际标签；未知时可建议 `enhancement`、`feature`、`configuration`、`message-forward`、`mute/ban`、`privacy`、`needs discussion`。

### 3. 配置默认值类 bug 判断
- 用户说“不填/为空”时，不要直接假设落盘值；需区分 key 缺失、`None`、`""`、`0`、`"0"`。`config.get(key, default)` 只处理缺失，不处理已存在的空值或 0。
- 若默认转发数量应为 20，而留空导致不转发，应倾向判为配置默认值 bug；优先级可表述为 low~medium，若首次安装默认空且影响核心功能可接近 high。
- 修复建议需保留显式 `0` 的关闭语义，不能简单用 `value or default`；缺失、None、空字符串可归一为默认值，`0`/`"0"` 仍表示关闭。还要考虑非法数字、负数、超过上限（如 100）的处理。
- 对 `ban_forward_history_count` 一类配置，要同步检查代码默认值、配置 schema、README/说明、设置 UI 保存行为；若 `int("")` 会异常回退 20，则“不填不转发”根因可能是 UI/schema 将空值保存为 0。
- 最小回归验证：缺失/None/空字符串→20，`0`/`"0"`→关闭，合法数字正常，非法输入回退或报错符合设计。

### 4. 重复检测与标签体系
- “未检测到重复”必须谨慎，除非说明检索依据；更稳妥写法是“暂未发现重复，但置信度较低/需结合历史 Issue 确认”。
- 对相关 Issue 应检索：禁言、mute、ban、合并转发、聊天记录、主人通知、配置项名（如 `ban_forward_history_count`）、不转发、默认值无效、空配置、配置项不填变成 0。
- 推荐标签前尽量对齐仓库现有标签集合；未知时也不能空白，至少给低风险标签 `bug` 或 `enhancement`。`good first issue` 仅在配置解析改动小、测试明确时中等置信推荐。
- 不要盲目把优先级塞进标题，除非仓库确有该风格；标题应聚焦业务对象、触发条件和异常/诉求。

### 5. 标题生成模板
- 功能请求：`支持在 Bot 被禁言时向主人转发禁言前聊天记录`；若强调配置：`支持配置 Bot 被禁言时转发给主人的历史聊天记录数量`。
- 配置默认值 bug：`转发聊天记录数量为空时未使用默认值` 或 `被禁言前转发聊天记录数量为空时未使用默认值`。
- 标题改写不要引入未提及结果（如崩溃/安全漏洞），也不要仅输出“无建议”。
