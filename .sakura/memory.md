# 代码审查经验总结

累计反思 17 次

## 一、审查规则

### 配置解析类（高优先级）

1. **空值与 0 语义必须分开**：不应使用 `value or default` 或 `if value`，当 0 是合法业务值时
2. **行为验证优先于编译检查**：配置解析修复必须有 `None/""/"0"/0/20` 等关键输入矩阵测试
3. **默认值集中定义**：避免在业务代码中多处硬编码
4. **小 PR 也查调用链**：确认解析结果类型、后续判断、已有配置兼容性

### 安全/隐私类（高优先级）

1. **权限边界检查**：消息转发/历史记录功能必须验证调用者身份和目标范围
2. **隐私标签体系**：涉及聊天记录转发的功能应标注 `privacy`/`security`
3. **操作审计日志**：敏感操作需记录谁在何时抽查了谁
4. **help wanted 不适合高复杂度/隐私功能**

### 输入与 API 类（中优先级）

1. **输入校验显式化**：命令参数需显式校验并给出友好错误
2. **API 失败降级**：外部 API 调用需有超时和降级处理
3. **缓存容量可配置**：硬编码的 `maxlen=100` 等应提取为配置项

## 二、Issue 分析规范

### 分类与标签

- 隐私敏感功能：补充 `privacy`(0.8)/`security`(0.5) 标签
- OneBot 兼容性问题：补充 `onebot`/`compatibility` 标签
- 复用现有逻辑：明确"复用范围"和"需扩展部分"

### 可行性评估

1. **消息来源必须明确**：群消息 vs 私聊的缓存机制是否已覆盖
2. **命令参数设计要具体**：给出方案而非仅说"需区分"
3. **关联历史 Issue**：不要只说"无重复"，应标注相关 Issue
4. **标题清晰时保留原标题**：不要强行改写

### 特殊场景

- **回读缓存问题**（如 `/QQ昵称`）：
  - 不等于修改失败
  - 应引入"已提交但未确认"中间态
  - 不能完全删除回读校验（历史背景）
  - 异步延迟需用 `asyncio.sleep`

## 三、代码模式

### 配置解析模式
```python
# ❌ 错误：0 会被错误处理
value or 20
if value:
    int(value or 0)

# ✅ 正确：显式区分
if value is None or value == "":
    return DEFAULT
elif value == 0 or value == "0":
    return DISABLE
else:
    return int(value)
```

### 缓存架构
```
handle_event → 私有缓存写入 → 命令处理 → 转发发送
deque(maxlen=N) 内存缓存，无持久化
```

## 四、经验教训

| 维度 | 核心要点 |
|------|---------|
| 配置解析 | 0 是高危配置值，边界值矩阵必须验证 |
| 隐私功能 | 标签必须体现安全风险，可行性要有合规评估 |
| 回读校验 | 引入中间态反馈，保留校验但优化提示 |
| 复用判断 | 不仅说明可复用，还需明确复用范围和差异点 |
| 类型问题 | IDE/mypy 可捕获的问题标记为 nitpick，不阻塞合并 |
