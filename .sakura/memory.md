## bot_responsible Issue 分析经验

### 1. 功能请求识别与降级兜底
- 遇到“加/新增/支持/希望”等诉求，尤其是“被禁言时向 Bot 主转发禁言前聊天记录、数量可配置”，应优先归类为 `feature` / `enhancement`，不要因标题无意义或模型/API 失败降为 `other`。
- 标题为“。”、空标题或纯符号时，必须从正文抽取核心意图生成标题，例如：`支持在 Bot 被禁言时向主人转发禁言前聊天记录`。
- 若 AI/API 429、格式校验失败或输出缺失，应启用本地规则兜底：关键词“禁言/转发/聊天记录/配置/合并转发”至少推出分类、基础标签、标题和谨慎可行性判断，避免结果完全空白。

### 2. 禁言转发类需求评估
- 该类需求通常优先级为 `medium`：对 Bot 管理、封禁溯源和群治理有价值，但非崩溃/安全阻断；若仅辅助功能或实现条件不足可降为 low。
- 可行性应拆为：是否能监听 Bot 自身被禁言事件、是否已有 per-group 最近消息缓存、是否支持合并转发、是否有配置系统、是否能只发给主人。
- 需要强调隐私/权限风险：自动转发群聊记录给 Bot 主可能涉及敏感信息，建议默认关闭、数量限制、权限边界清晰，必要时标记 `privacy` / `needs discussion`。
- 标签建议优先贴合仓库实际标签；未知时可建议 `enhancement`、`feature`、`configuration`、`message-forward`、`mute/ban`、`privacy`、`needs discussion`。

### 3. 配置默认值类 bug 判断
- 用户说“不填”时，不要直接假设落盘值；需区分 key 缺失、`None`、`""`、`0`、`"0"`。`config.get(key, default)` 只处理缺失，不处理已存在的空值或 0。
- 若默认转发数量应为 20，而留空导致不转发，应倾向判为配置默认值 bug；但优先级可表述为 low~medium，取决于功能核心程度和是否可手动填写规避。
- 修复建议需保留显式 `0` 的关闭语义，不能简单用 `value or default`；缺失、None、空字符串可归一为默认值，`0`/`"0"` 仍表示关闭。
- 配置问题要同步检查代码默认值、配置 schema、README/说明和设置 UI 保存行为，并补充最小回归验证。

### 4. 重复检测与标签体系
- “未检测到重复”必须谨慎，除非说明检索依据。对相关 Issue 应检索：禁言、mute、ban、合并转发、聊天记录、主人通知、配置项名（如 `ban_forward_history_count`）、不转发、默认值无效。
- 推荐标签前应尽量对齐仓库现有标签集合；不要盲目使用通用标签或把优先级塞进标题，除非仓库确有该风格。
