## 3. 规范完善建议

### 建议新增审查规则

1. **配置解析必须区分空值、默认值和显式关闭**
   - 对数值型配置，不能使用：
     ```python
     value = int(config.get("x", default) or default)
     ```
     如果 `0` 是合法值，这会误伤关闭语义。
   - 推荐规则：
     - key 缺失 → 默认值
     - `None` → 默认值
     - `""` / 纯空白字符串 → 默认值
     - `"0"` / `0` → 保留为 0
     - 非数字 → 默认值或明确报错
     - 越界值 → 按项目既有规则处理

2. **配置项应有统一解析函数**
   - 对类似配置建议抽出工具函数，例如：
     ```python
     def parse_int_config(value, default, min_value=None, max_value=None):
         ...
     ```
   - 避免每个配置项独立写一套 `try/int/strip/default` 逻辑。

3. **数值配置修改必须附带边界用例说明**
   - 即使没有自动化测试，PR 描述或审查评论中也应明确验证：
     - 缺失
     - `None`
     - 空字符串
     - 空白字符串
     - `"0"`
     - 合法数字
     - 非法字符串
     - 越界值

4. **异常捕获范围需最小化**
   - 对 `int()` 转换建议捕获：
     ```python
     except (TypeError, ValueError):
     ```
   - 避免裸 `except` 掩盖其他逻辑错误。

5. **配置行为需同步检查文档和 schema**
   - 如果修改了配置默认值、空值语义、范围限制，应检查：
     - 默认配置文件
     - 配置 schema
     - README
     - 插件设置面板说明
   - 尤其是用户可见配置项，文档中的“为空时默认 20”应与实际一致。

### 项目特有规范要点

针对 `ban_forward_history_count` 建议固化以下语义：

| 输入 | 期望结果 |
|---|---|
| key 缺失 | `20` |
| `None` | `20` |
| `""` | `20` |
| `"   "` | `20` |
| `0` | `0` |
| `"0"` | `0` |
| `"5"` | `5` |
| 非法字符串 | `20` |
| 负数 | 按既有范围规则处理，建议回退默认或限制到 0 |
| 大于 100 | 按既有范围规则处理，建议回退默认或限制到 100 |

同时建议明确：

- `0` 表示不转发历史记录；
- 空值不是关闭，而是使用默认值；
- 默认值为 20；
- 最大值为 100；
- 该功能涉及群聊记录转发，应在配置说明中提示隐私风险。

## 4. 经验教训

### 未来审查重点

1. **不要只验证 happy path**
   - 配置解析类变更最容易在边界值出问题。
   - 特别是空字符串、空白字符串、`"0"`、`0`、非法字符串，必须单独确认。

2. **警惕 `or default`**
   - 这是 Python 配置解析中的常见陷阱。
   - 当 `0`、`False`、空列表等是合法显式值时，不能用布尔短路回退默认值。

3. **区分“缺失”和“已配置为空”**
   - `config.get(key, default)` 只处理 key 缺失。
   - 如果 key 存在但值为 `""`，不会使用 default。
   - 这是本类 bug 的根源之一。

4. **审查时应反查 UI/schema 行为**
   - Issue 来源是“插件设置不填”，所以配置面板保存出的实际值非常重要。
   - 仅在运行时兜底可能解决问题，但如果 UI 显示、schema 默认值和代码默认值不一致，后续还会产生误解。

5. **小修复也应建议最小测试矩阵**
   - 本次变更只有 `+4/-3`，看似简单，但语义边界多。
   - 小改动不一定低风险，尤其是配置默认值和关闭开关共存时。

6. **隐私相关配置需要额外敏感**
   - 该功能会转发群聊历史记录给主人。
   - 即使本次不是新增功能，也要确认修复不会意外扩大转发范围。
   - 默认转发 20 条是否符合项目已有约定可以接受，但未来若调整默认开启/关闭，应重点审查隐私影响。
