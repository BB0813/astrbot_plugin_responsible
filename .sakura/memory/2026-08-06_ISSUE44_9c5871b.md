# Issue #44 深度反思

## 一、Issue 实际内容还原**

标题是逗号"，"——纯标点，无意义标题。正文：`/QQ昵称 福瑞` + 错误提示（set_qq_profile 调用成功但读取到昵称是"小Q"而非"福瑞"，列出三个可能原因） + `合并加重新安装了`。

这是 bot_responsible 项目（基于 OneBot 协议的 QQ Bot 工具），用户使用 `/QQ昵称` 指令尝试修改昵称为"福瑞"，调用 OneBot 的 `set_qq_profile` 接口成功但读取到的昵称未生效。

## 二、逐维度反思**

### 1. 分类与优先级准确性 ❌ 严重失误**

**问题：**
- 分类为 `other` 是兜底失败的结果，根因是 AI 输出格式校验失败（`expected <SUGGESTED_TITLE>`），而不是经过判断后认为"其他"。
- 这是一个明确的 **`bug` / `support` 报告**——用户报告了指令行为与预期不符，并提供了 API 调用结果、读取结果不一致的事实。

**正确分类应该考虑：**
- `bug`：set_qq_profile 返回成功，昵称未实际变更，行为与指令语义不一致。
- `support / question`：用户也可能只是在询问"为什么没生效"，因为错误提示里已经给了三个可能原因，最后一句"合并加重新安装了"像是用户在追加说明操作过程。

**优先级判断缺失：**
- 该问题影响单个用户使用 `/QQ昵称` 指令，影响面有限但属于核心用户配置能力。
- 合理优先级：`low`～`medium`（不影响 Bot 主流程，但功能不可用）。
- 项目记忆中没有专门覆盖此类问题，应新建经验。

**反思：**
- 当 AI 输出格式校验失败时，**不能直接输出"无法评估"和"无建议"**，必须启用本地规则兜底。
- Issue 正文包含命令 + 失败描述 + 可能原因 + 后续操作，这是典型的"用户报告问题"结构，不应归为 other。

### 2. 标签推荐质量 ❌ 完全缺失**

**问题：**
- 建议标签为空。这是 AI 输出失败后的连锁失误。

**应该推荐的标签：**
- `bug`：行为与指令语义不符。
- `support` 或 `question`：用户可能在寻求帮助。
- `onebot`：问题根因在 OneBot 实现层。
- `profile` 或 `nickname`：与用户资料/昵称相关。
- `needs-triage`：需要确认是 Bot 端问题还是 OneBot 端限制。

**反思：**
- 项目记忆明确写"未知时也不能空白，至少给低风险标签 `bug` 或 `enhancement`"，本次完全违反。
- 标签应至少反映：问题类型（bug/support）+ 涉及模块（onebot/profile）。

### 3. 可行性判断质量 ❌ 标注"无法评估"是失职**

**问题：**
- 可行性应为"无法评估"实际上意味着放弃了分析。

**应该做的可行性拆解：**
- **技术依赖：** set_qq_profile 是 OneBot 标准接口，但昵称字段属于扩展能力，不同实现（go-cqhttp、LLOneBot、官方 QQ）支持程度差异大。
- **可能根因：**
  1. OneBot 实现端不支持 nickname 参数（最可能）；
  2. 协议层接口文档与实际后端能力不匹配；
  3. Bot 代码未处理 set_qq_profile 返回值与实际生效的偏差（缺少读取回验）；
  4. QQ 风控/账号类型（企业号、长时间未登录）导致修改被静默丢弃。
- **代码侧可改进点：**
  - 在调用 set_qq_profile 后用 get_qq_profile 回读并对比，失败时给用户更明确的提示。
  - 在 README 中标注 OneBot 实现的兼容性矩阵。
  - 区分签名、昵称、头像三类参数的支持情况。
- **工作量估算：** 小～中等，主要是完善调用回验和文档说明。
- **风险：** 涉及账号安全与平台合规，不要在代码层强制绕过 OneBot 接口做非常规调用。

### 4. 重复检测准确性 ⚠️ 未检测但缺乏依据**

**问题：**
- 输出"未检测到重复"但未说明检索依据，符合项目记忆中"必须谨慎，除非说明检索依据"的告诫标注。
- 但本次因为 AI 输出失败，没有机会真正去检索。

**应该检索的关键词：**
- `/QQ昵称`、`set_qq_profile`、`昵称`、`profile`、`onebot`、`小Q`、昵称不生效、set_qq_profile 失败、修改昵称。

**反思：**
- 在 bot_responsible 这种中小型工具项目中，重复 Issue 比较常见，尤其是涉及特定指令（`/QQ昵称`、`/群管理`）和 OneBot 接口的。
- 项目记忆中提到的禁言转发类需求检索关键词非常具体，本类问题也应建立专门的检索关键词库。

### 5. 标题改写适当性 ❌ 输出"无建议"违反项目记忆**

**问题：**
- 项目记忆明确写"标题为'。'、空标题或纯符号时，必须从正文抽取核心意图生成标题，例如：`支持在 Bot 被禁言时向主人转发禁言前聊天记录`"。
- 本次原标题是"，"（纯标点），更应启用该兜底规则。

**建议标题候选：**
- `使用 /QQ昵称 修改昵称后未生效（set_qq_profile 返回成功但读取不一致）`
- `/QQ昵称 指令修改昵称失败：API 返回成功但昵称仍为原值`
- `set_qq_profile 修改昵称无效，疑似 OneBot 实现不支持 nickname 参数`

推荐第一个，因为最完整地保留了用户原始场景（`/QQ昵称` 指令）+ 现象（修改后未生效）+ 关键事实（API 返回成功但读取不一致）。

**反思：**
- 输出"无建议"是项目记忆第 1 条明确禁止的情况。
- 即使 AI 失败，本地规则也应该能根据"标题纯符号"这一明确信号触发兜底逻辑。

### 6. 经验教训——本次失败的核心教训**

**核心教训 1：AI 失败 ≠ 分析失败**
本次所有字段都退化成"无法评估/无建议/未检测到重复"，本质上是把 AI 输出的格式校验错误当成了"无法分析"的信号。正确做法是：
- 识别格式校验失败后立即切换到本地规则兜底；
- 哪怕 AI 完全失效，也必须输出最低限度的分类、标签、标题建议。

**核心教训 2：bot_responsible 的 Issue 模式新增一类**
项目记忆中已覆盖的功能请求、配置默认值 bug、禁言转发类需求，都属于"用户提出需求/报告异常"的范畴。本次新增一种模式：
- **OneBot 接口能力差异导致的指令失效**：用户使用 `/XXX` 类指令，Bot 调用 OneBot 接口，但接口在不同 OneBot 实现下支持程度不同，导致行为与用户预期不一致。
- 这类问题应优先归类为 `bug` 或 `support`；
- 标签建议：`bug`、`onebot`、`profile`（按具体功能）、`needs-triage`；
- 优先级通常 `low`～`medium`；
- 标题模板：`使用 /{指令} {参数} 后未生效（{OneBot 接口} 返回与实际行为不一致）`；
- 可行性上重点分析 OneBot 兼容性和是否需要在 Bot 侧做调用回验。

**核心教训 3：错误提示 + 后续操作 = 强烈信号**
"合并加重新安装了"出现在错误提示之后，强烈暗示用户已经做过基础排障（重装、合并代码），问题仍未解决。这通常意味着：
- 不是简单的安装/环境问题；
- 应该提高对根因分析（OneBot 兼容性、Bot 代码逻辑）的权重；
- 优先级可以比普通"刚提报的问题"略高。

**核心教训 4：bot_responsible 的指令集是分析入口**
项目里有 `/QQ昵称`、`/群管理` 等指令。任何 Issue 只要以 `/XXX` 开头，几乎都是功能使用报告，可以从指令名反推涉及的功能模块（昵称、群管、配置等）。这是项目特有的模式，应作为快速分类信号。
