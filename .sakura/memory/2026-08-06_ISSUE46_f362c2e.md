## Issue #46 分析反思

### 1. 分类与优先级准确性

**原分析分类为 `other` 不准确。**

该 Issue 标题和正文都非常明确：

- 标题：`[feature][low] 支持配置通知 QQ 号接收插件通知`
- 内容：希望在插件配置中增加“通知 QQ 号”，用于接收插件通知。

这明显是一个**功能请求 / 配置增强**，更合适的分类应为：

- `feature`
- 或 `enhancement`
- 可进一步细分为 `configuration` / `notification`

原分析之所以给出 `other`，主要是因为分析流程出现了格式校验失败：

> AI Issue analysis output could not be validated: expected `<SUGGESTED_TITLE>`

但格式失败不应导致语义分析降级为空洞结果。根据已有项目经验，遇到 `[feature]`、`支持配置`、`加一个` 等关键词时，应启用本地规则兜底，至少能判断为功能请求。

**优先级 `medium` 偏高。**

原 Issue 标题中已明确标注 `[low]`，正文也表明这是一个通知接收人的配置扩展，不是核心功能阻断、崩溃、安全问题或数据丢失。

更合理的优先级应为：

- `low`

除非该插件通知机制是项目核心能力，并且当前没有通知 QQ 号会导致通知完全不可用，否则不应提升为 `medium`。

**实际影响范围：**

该功能主要影响：

- 插件通知的接收方式；
- Bot 主或管理员是否能收到插件事件提醒；
- 多账号 / 指定账号通知场景。

影响范围有限，属于体验增强和配置灵活性提升。

### 3. 可行性判断质量

原分析给出“无法评估”，过于保守。

从 Issue 描述来看，功能需求很小且明确：

> 在插件配置加一个通知 QQ 号，可以给填写的 QQ 号通知。

一般实现上需要考虑：

1. **配置项新增**
   - 新增类似 `notify_qq`、`notification_qq`、`notice_qq` 的配置字段；
   - 支持为空，表示不发送或使用默认接收者；
   - 可选支持多个 QQ 号。

2. **通知发送逻辑**
   - 在插件已有通知触发点中读取配置；
   - 如果配置了 QQ 号，则向该 QQ 发送私聊通知；
   - 如果未配置，则保持当前行为。

3. **权限与有效性校验**
   - QQ 号格式校验；
   - Bot 是否能主动私聊该 QQ；
   - 该 QQ 是否为好友；
   - 平台是否允许主动消息。

4. **兼容性**
   - 需要避免破坏当前通知逻辑；
   - 需要考虑旧配置文件升级；
   - 需要 README 或配置示例同步更新。

因此可行性应评估为：

- **可行性：较高**
- **工作量：低到中等**
- **主要风险：平台私聊权限、配置兼容、通知对象权限控制**

原分析没有结合 Issue 文本进行基本拆解，直接“无法评估”不合理。

### 6. 经验教训

#### 6.1 遇到显式 `[feature]` 标记应高权重处理

该 Issue 标题中已经有 `[feature][low]`，分析器应优先采用：

- 分类：`feature` / `enhancement`
- 优先级：`low`

除非正文与标题明显矛盾，否则不应因为分析输出格式错误而改成 `other` 或 `medium`。

#### 6.2 格式校验失败不能让分析结果语义失效

这次原分析的核心问题不是 Issue 难以判断，而是分析输出格式失败后没有兜底：

```text
AI Issue analysis output could not be validated: expected <SUGGESTED_TITLE>
```

未来应增加本地规则：

- 标题含 `[feature]`、`支持`、`新增`、`配置` → `feature/enhancement`
- 标题含 `[low]` → 优先级倾向 `low`
- 正文含“加一个配置项” → 可行性通常较高
- 标题清楚时也要给出“建议保留”或轻微优化标题，不能输出“无建议”

#### 6.3 配置类功能请求通常工作量较低，但要关注边界

此类需求看似简单，但仍需确认：

- 单个 QQ 还是多个 QQ；
- 是否支持群号；
- 未配置时的默认行为；
- 配置变更是否热加载；
- Bot 能否私聊目标 QQ；
- 通知内容是否涉及敏感信息；
- 是否仅允许管理员配置。

#### 6.4 标签不应为空

即使无法获取仓库现有标签，也应给出低风险通用标签：

```text
enhancement, configuration
```

对于本 Issue，可以再加：

```text
notification
```

#### 6.5 更合理的修正后分析结果

建议将该 Issue 修正为：

```text
分类: feature / enhancement
优先级: low
可行性: 较高
建议标签: enhancement, configuration, notification
建议标题: 支持配置接收插件通知的 QQ 号
重复检测: 暂未发现重复，但需检索“通知 QQ / notification / notify / 配置通知”等关键词确认
```

总体来看，原分析主要失败点是**格式校验失败后没有语义兜底**，导致分类、优先级、标签、标题和可行性全部退化。这个 Issue 本身非常明确，未来同类需求应按配置增强类功能请求处理。
