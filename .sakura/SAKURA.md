# 项目概述：bot_responsible – AstrBot 人际关系管理插件

累计反思 12 次

## 1. 项目简介

这是一个为 [AstrBot](https://github.com/AstrBotDevs/AstrBot) 开发的人际关系管理插件，面向 QQ/OneBot 场景，提供黑名单、好友/群组、请求处理、通知与被动防护能力，帮助 Bot 管理员维护社交关系安全。

核心能力包括：
- 黑名单管理：拉黑/解封用户与群组，自动拒绝黑名单用户申请或邀请，Bot 被踢后自动拉黑群，被拉入黑名单群后自动退出。
- 好友与群组管理：查看好友/群列表，删除好友、退群；主动加好友/加群在 SnowLuma 下依赖实验性 `send_packet`，不是标准 OneBot 能力。
- 请求处理：监听 SnowLuma 标准 `request.friend`、`request.group` 事件，支持待处理列表、编号处理、引用通知快速同意/拒绝/拉黑。
- 通知机制：支持设置通知群；未设置通知群时通过私聊通知管理员。
- 禁言防护：监听 Bot 被群禁言事件，向 Bot 主通知并合并转发禁言前最近 N 条群聊记录；数量由 `ban_forward_history_count` 配置，`0` 表示关闭，最大 `100`。
- Bot 资料能力：`/QQ昵称`、`/设置头像` 等依赖 OneBot/平台实现能力，需承认适配器差异与 QQ 风控限制。

## 2. 技术栈

- **语言**：Python 3.8+
- **框架**：AstrBot 插件体系
- **协议/适配**：OneBot v11/v12；部分 SnowLuma 标准事件与实验能力
- **数据存储**：本地 JSON 文件持久化
- **许可证**：MIT

## 4. 开发约定

- **事件驱动**：围绕好友申请、群请求、群成员变化、Bot 被踢/被拉入/被禁言等事件触发自动处理。
- **管理员命令**：命令以 `/` 开头，支持中文命令与英文别名，例如 `/好友` `/fl`、`/拉黑` `/addbl`、`/同意` `/accept`。
- **权限控制**：管理类命令仅管理员可用；自动拒绝黑名单请求等被动逻辑不依赖人工权限操作。
- **引用与编号处理**：请求通知可通过引用消息快速处理，也可用待处理编号处理，需保证 pending 数据与通知内容一致。
- **配置一致性**：代码默认值、配置 schema、README 必须保持一致；尤其是 `ban_forward_history_count` 和通知接收人配置。
- **实验/兼容能力标注**：主动加好友/加群依赖 SnowLuma `send_packet`；QQ 昵称/资料修改依赖 OneBot 实现与平台能力，文档和提示中需明确标注风险。

## 5. 当前重点经验：配置解析、通知与禁言历史转发

### 5.1 `ban_forward_history_count` 配置规则

配置项语义应保持为：
- 缺失、`None`、空字符串、纯空白字符串：使用默认值 `20`；
- 显式 `0` 或字符串 `"0"`：关闭缓存与转发；
- 正整数：按配置值生效；
- 大于 `100`：限制为 `100`；
- 非法值：回退默认值或给出明确提示；
- 修复时禁止用简单的 `value or default`，否则会破坏显式 `0` 的关闭语义。

配置问题排查时必须区分：字段缺失、空字符串、空白字符串、`None`、`0`、`"0"`。`config.get(key, default)` 只能处理字段缺失，不能自动处理 key 存在但值为空/无效的情况。

建议建立统一解析函数，例如：`parse_int_config(value, default, min_value, max_value, allow_zero=True)`，捕获 `TypeError`/`ValueError`，避免裸 `except`。配置解析类 PR 至少说明或测试：缺失、`None`、`""`、`"   "`、`0`、`"0"`、合法数字、非法字符串、负数、超上限。

### 5.2 禁言历史转发实现与审查要点

- “Bot 被禁言时向 Bot 主合并转发禁言前聊天记录，且数量可配置”属于 **feature/enhancement**；默认值/空值不生效属于 **bug**。
- 技术依赖：监听群禁言事件并判断 Bot 自身；禁言前持续缓存每群最近 N 条消息；适配器支持合并转发或降级；配置项控制数量与开关。
- 该功能涉及群聊内容自动转发给主人，具有隐私风险。应限制数量、支持关闭、只发给主人/管理员，并在文档中说明。
- 审查相关 PR 时不能只看 `py_compile` 或 happy path，应检查 README/schema/UI 默认值是否同步，以及缓存阶段和发送阶段是否都遵守解析后的数量。

### 5.3 通知配置扩展经验

新增“通知 QQ 号/指定私聊接收人”属于通知能力增强，通常分类为 `feature`/`enhancement`，优先级 `low`，若项目重视通知可靠性可到 `medium`。标签可考虑 `configuration`、`notification`、`needs discussion`。

设计时必须明确：
- 支持单个 QQ 还是多个 QQ；字段名如 `notify_user`/`notify_users`/`notify_qq`；字符串、数字、列表的兼容解析。
- 通知群、指定 QQ、管理员私聊之间的优先级：只发一个、同时发送，还是失败后兜底。
- 私聊可能受好友关系、平台权限、风控、适配器能力限制；发送失败不能影响后续接收人。
- 修改配置要同步 schema、初始化解析、业务通知路径、禁言历史转发路径、README 和命令说明。

## 6. Issue 分析与维护经验

- 遇到标题为“。”、“，”或纯符号的 Issue，必须从正文中提取核心诉求并生成可读标题，不应输出“无建议”。标题中不要盲目加入 `[feature]`/`[low]`，除非仓库确有该风格。
- `[feature]`、`[bug]`、`[medium]` 等标题标记是高权重线索：若正文一致，应增强分类/优先级置信度；但优先级仍需结合实际影响范围判断。
- 功能请求常见标签：`enhancement`/`feature`、`configuration`、`notification`、`needs discussion`；涉及聊天记录转发时考虑 `privacy`/`security`。
- 配置默认值问题通常应标为 `bug`，并推荐 `configuration`、`default-value`、`settings`、`forwarding` 等标签。
- 重复检测不能只说“未检测到重复”，应说明检索关键词。没有历史数据时表述为“暂未发现重复，置信度有限”。
- 若外部 AI/API 分析失败、限流或结构化输出校验失败，必须有本地规则兜底：关键词分类、基础标签、标题改写、重试/降级提示，避免退化为 `other`、无标签、无法评估。
- 可行性分析即使缺少完整代码，也应拆解技术依赖、工作量和风险，而不是直接“无法评估”。

## 7. OneBot 接口能力差异类问题

近期 `/QQ昵称` Issue 暴露了新模式：用户使用 `/XXX` 指令，插件调用 OneBot 接口并返回成功，但实际状态未变化或回读不一致。这类问题应按“兼容性/上游能力问题导致的功能失败”处理。

分析规则：
- 优先归类为 `bug` 或 `support/question`，如果仓库有 `compatibility`、`upstream`、`external`、`needs info` 更贴切；优先级通常 `low`，影响广泛时再到 `medium`。
- 标签至少保留问题类型，不得空白；可建议 `bug`、`onebot`、`profile`/`nickname`、`needs-triage`/`needs info`。
- `/XXX` 开头的 Issue 往往是功能使用报告，应从指令名反推模块，例如 `/QQ昵称` → profile/nickname，群相关命令 → group。
- 标题模板：`使用 /{指令} 修改后未生效（{OneBot action} 返回成功但回读不一致）`；例如：`/QQ昵称 调用成功后回读昵称仍未变化`。
- 重复检测应检索 `/QQ昵称`、`set_qq_profile`、`昵称`、`nickname`、`profile`、`onebot`、`小Q`、`修改昵称失败` 等，并说明相似依据；只有“可能重复 #44”时不要给 `duplicate` 过高置信度。

排查与修复建议：
- 要求用户补充 OneBot 实现及版本、机器人账号类型、原始 action 返回、回读接口返回、是否延迟后仍不生效、是否可用客户端手动修改。
- 区分“设置失败”和“回读缓存未刷新”：可考虑延迟二次回读，但不能承诺必定修复。
- 插件侧可改进失败提示、日志与诊断信息，记录 action 名称、参数、retcode/message/wording、回读接口和字段。
- README 应标注 `/QQ昵称` 等资料修改命令依赖实现支持，必要时列出已知支持/不支持的 OneBot 实现；不要为了绕过限制使用非常规或高风险方式。

## 8. 维护注意事项

- README、配置 schema、代码逻辑要同步更新，避免用户界面“不填”行为与文档默认值不一致。
- 自动转发群聊记录应审慎处理隐私：限制数量、仅发给主人/管理员、必要时支持关闭或脱敏。
- SnowLuma/OneBot 差异要在用户文档中保持清晰，避免把实验路径写成标准能力。
- 新增或修改配置时优先使用统一解析函数，避免每个功能自行处理空值、非法值、上限和关闭语义。
- 小型 PR 也应留下边界用例或非阻断测试建议，特别是配置默认值、关闭开关、通知链路和外部 API 兼容性相关改动。
