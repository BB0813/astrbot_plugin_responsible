# 项目概述：bot_responsible – AstrBot 人际关系管理插件

累计反思 5 次

## 1. 项目简介

这是一个为 [AstrBot](https://github.com/AstrBotDevs/AstrBot) 开发的人际关系管理插件，面向 QQ/OneBot 场景，提供黑名单、好友/群组、请求处理、通知与被动防护能力，帮助 Bot 管理员维护社交关系安全。

核心能力包括：
- 黑名单管理：拉黑/解封用户与群组，自动拒绝黑名单用户申请或邀请，Bot 被踢后自动拉黑群，被拉入黑名单群后自动退出。
- 好友与群组管理：查看好友/群列表，删除好友、退群；主动加好友/加群在 SnowLuma 下依赖实验性 `send_packet`。
- 请求处理：监听 SnowLuma 标准 `request.friend`、`request.group` 事件，支持待处理列表、编号处理、引用通知快速同意/拒绝/拉黑。
- 通知机制：支持设置通知群；未设置通知群时通过私聊通知管理员。
- 禁言防护：监听 Bot 被群禁言事件，向 Bot 主通知并合并转发禁言前最近 N 条群聊记录；数量由 `ban_forward_history_count` 配置，`0` 表示关闭，最大 `100`。

## 2. 技术栈

- **语言**：Python 3.8+
- **框架**：AstrBot 插件体系
- **协议/适配**：OneBot v11/v12；部分 SnowLuma 标准事件与实验能力
- **数据存储**：本地 JSON 文件持久化
- **许可证**：MIT

## 4. 开发约定

- **事件驱动**：围绕好友申请、群请求、群成员变化、Bot 被踢/被拉入/被禁言等事件触发自动处理。
- **管理员命令**：命令以 `/` 开头，支持中文命令与英文别名，例如 `/好友` `/fl`、`/拉黑` `/addbl`、`/同意` `/accept`。
- **权限控制**：管理类命令仅管理员可用；自动拒绝黑名单请求等被动逻辑不依赖人工权限操作。
- **引用与编号处理**：请求通知可通过引用消息快速处理，也可用待处理编号处理，需保证 pending 数据与通知内容一致。
- **配置一致性**：代码默认值、配置 schema、README 必须保持一致；尤其是 `ban_forward_history_count`。
- **实验能力标注**：主动加好友/加群依赖 SnowLuma `send_packet`，不是标准 OneBot 能力，文档和提示中需明确标注风险。

## 5. 当前重点经验：禁言历史转发与配置默认值

近期 Issue #37/#39 围绕“Bot 被禁言时合并转发禁言前聊天记录”及其配置默认值展开，形成以下项目知识：

### 功能性质与实现要点

- “Bot 被禁言时向 Bot 主合并转发禁言前聊天记录，且数量可配置”应归类为 **feature/enhancement**，不是 `other`。
- 技术上依赖四点：
  1. 能监听群禁言事件，并判断被禁言对象是否为 Bot 自身；
  2. 在禁言发生前持续缓存每个群最近 N 条消息；
  3. 适配器支持合并转发；不支持时需考虑降级为普通文本/摘要；
  4. 配置项控制转发数量与开关。
- 该功能涉及群聊内容自动转发给 Bot 主，具有隐私与权限风险。设计上应限制权限、记录数量可控，并在文档中明确说明。

### `ban_forward_history_count` 配置规则

配置项语义建议保持为：
- 缺失、`None`、空字符串：使用默认值 `20`；
- 显式 `0` 或字符串 `"0"`：关闭缓存与转发；
- 正整数：按配置值生效；
- 大于 `100`：限制为 `100`；
- 非法值：回退默认值或给出明确提示；
- 修复时禁止用简单的 `value or default`，否则会破坏显式 `0` 的关闭语义。

配置问题排查时必须区分：字段缺失、空字符串、`None`、`0`、`"0"`。`config.get(key, default)` 只能处理字段缺失，不能自动处理 key 存在但值为空/无效的情况。

建议为整数配置建立统一解析函数，例如：`parse_int_config(value, default, min_value, max_value, allow_zero=True)`，并为以下场景补充回归验证：缺失、空字符串、`None`、`0`/`"0"`、正常正整数、超上限、非法字符串。

## 6. Issue 分析与维护经验

- 遇到标题为“。”或纯符号的 Issue，必须从正文中提取核心诉求并生成可读标题，不应输出“无建议”。
- `[feature]`、`[bug]`、`[medium]` 等标题标记可作为线索，但分类和优先级仍需结合正文与实际影响判断。
- 功能请求常见标签：`enhancement`/`feature`、`configuration`、`message-forward`、`mute`/`ban`、`needs discussion`；涉及聊天记录转发时应考虑 `privacy`/`security` 风险标签。
- 配置默认值问题通常应标为 `bug`，但优先级可在 `low ~ medium` 间评估：若功能核心且影响广泛取 medium；若有简单规避方式（手动填写值）可偏 low。
- 重复检测不能只说“未检测到重复”，应说明检索关键词，例如：禁言、mute、ban、合并转发、聊天记录、默认值、不转发、`ban_forward_history_count`。
- 若外部 AI/API 分析失败或限流，流程必须有本地规则兜底：关键词分类、基础标签、标题改写、重试/降级提示，避免结果退化为 `other`、无标签、无法评估。

## 7. 维护注意事项

- 修改禁言历史转发时要同时检查缓存阶段和发送阶段：若配置 `<= 0`，二者可能都会跳过。
- README、配置 schema、代码逻辑要同步更新，避免用户界面“不填”行为与文档默认值不一致。
- 自动转发群聊记录应审慎处理隐私：限制数量、仅发给主人/管理员、必要时支持关闭或脱敏。
- SnowLuma/OneBot 差异要在用户文档中保持清晰，避免把实验路径写成标准能力。
